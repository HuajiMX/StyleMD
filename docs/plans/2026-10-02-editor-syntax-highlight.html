源码编辑器高亮样式 · 实施规划

2026-10-02 ｜ 仓库：E:\projects\StyleMD ｜ 分支：main（工作区干净）｜ 状态：待评审，未动实现代码

北极星：让工作台左侧的源码区从「一视同仁的灰字」变成「一眼看得出文档结构、也看得见自己正在改哪一段」的编辑器—— Markdown 语法按 StyleMD 自己的调色板上色，光标所在结构在源码里同步高亮；而这次改动不触碰 core、 样式模型、以及预览与导出的共用渲染路径。

1范围与边界

本次要做

  • 换掉源码区的编辑内核：把 apps/demo 的受控 <textarea> 换成规划 §15 已选定的 CodeMirror 6。
  • Markdown 语法高亮：前置元数据、标题及其标记、强调/加粗、行内代码、围栏代码块、链接、引用、列表标记、分隔线、表格竖线各有稳定色调。
  • 结构高亮：光标所在「角色块」（复用 collectRoleSpans 的原文偏移）整体淡染 + 左侧竖条，当前行再叠一层更淡的底色。
  • 高亮配色可调：全部颜色收敛为工作台 CSS 变量，一处改、全局生效，为后续深色主题与 M3 代码块主题留接口。
  • 保住既有能力：光标 → 样式卡片定位、编辑器→预览滚动同步、预览→编辑器反向滚动、大纲当前章节高亮、会话光标恢复、字数统计、视图模式与宽度拖拽，逐条回归验证。

本次不做（非目标）

  • 不改 packages/core、packages/theme-schema、packages/presets、packages/renderer-paged：编辑器高亮属于宿主 UI 层，不是渲染内核的职责。
  • 不改 build() 产出的 HTML/CSS，预览与导出路径一行不动（架构约束 3：预览与导出共用同一份 HTML）。
  • 不做渲染输出侧的代码块语法高亮（Shiki），那是规划 §6「代码」行 + M3 的范围；本次只做编辑器里的语法上色，两者共用一份调色板但不共用实现。
  • 不做深色工作台主题、搜索替换、多光标批量编辑、代码折叠、行号槽、Vim 键位。
  • 不做 WYSIWYG 或编辑器内嵌预览——本项目定位是「用户继续写 Markdown 源码，只是不用手写 CSS」（规划 §4 假设）。

假设

  • 接受规划 §15 的编辑器选型（CodeMirror 6），本次不重新论证「该不该自己写编辑器」。
  • 允许安装 npm 依赖；允许改 demo 与 e2e 的包内结构。
  • 本机 Chromium 可用，node e2e/smoke.mjs 能跑（沿用既有约定，可用 STYLEMD_CHROME 指定）。
  • 性能目标沿用规划 M2 验收：50 页量级文档，输入延迟 < 50ms、预览刷新 ≤ 300ms。

权限边界

可动：apps/demo/**、e2e/**、apps/demo/package.json 依赖、apps/demo/src/styles.css、本规划文档。
请示后再动：任何 packages/* 的改动、tsconfig.json / vite.config.ts 的别名变更、schemaVersion 与迁移逻辑。
不动：预览 iframe 的沙箱与 CSP 策略（App.tsx 的 PREVIEW_CHROME_CSS / sandbox 注入）。

2待定决策

先看这四条：它们决定工作量和风险面，其余细节都建立在这里的答案之上。决策人：项目所有者。

Q1 · 迁移节奏：分两步还是一次换掉？

一次替换要同时动 App 的 6 处滚动/光标逻辑、组件、样式与 15 处 e2e 断言。出问题时很难判断是「抽象没抽对」还是「新编辑器行为不同」。

分两步则是：PR A 只做行为等价的重构（把 HTMLTextAreaElement 换成一层编辑器句柄），PR B 才把实现换成 CodeMirror 6。

建议：分两步。PR A 结束时全部既有测试必须仍然通过，把「重构引入的问题」和「新编辑器引入的问题」隔离在两次提交里；回滚也只需 revert PR B。详见 §9、§14。

相关：§7 方案与替代 · §12 风险

Q2 · 结构高亮要不要和语法高亮同一批交付？

语法高亮解决「读得清」，结构高亮解决「知道自己在改哪个角色」。两者都用 CodeMirror 的 Decoration 机制，共用同一个插件入口；但拆开做要多改一轮 e2e。

建议：同一批交付，但视觉权重分清主次——语法上色用色相区分，结构高亮只用极淡底色 + 左侧竖条，避免两种高亮互相盖住。详见 §6。

相关：§5 目标行为 · §6 交互与视觉

Q3 · 高亮配色归工作台还是归样式包？

样式包（*.stylemd.json）描述的是「文档渲染到纸上的样子」；编辑器是宿主 chrome，用户导出的样式包不该改变工作台自己的界面配色。

建议：归工作台 CSS 变量（--syn-*）。同时把这组变量与 M3 的代码块主题预留为同一份调色板源，避免以后两套颜色各自漂移。详见 §8。

相关：§8 模型与依赖影响 · §6 调色板

Q4 · 正文文字要不要也上色？

把整行染成彩色会让长文阅读变累，也让低对比度配色通过不了可读性要求。

建议：正文文字保持 --ink（#17202e）不动，只给结构标记与行内标记上色（#、-、反引号、链接、引用符号）。标题只加粗加深，不改字号，避免行高抖动影响滚动定位。详见 §6。

相关：§6 交互与视觉

apps/demo/src/styles.css :root 已有一整套工作台 token（--panel / --ink / --accent / --mono …，color-scheme: light）；.source-pane / .source-input 是唯二与源码区相关的选择器，可原位承接到新的编辑器容器上。

5目标行为

  1. 打开即上色：文档加载后 1 帧内源码区已按语法着色，无闪烁、无「先黑后彩」的过渡。
  2. 边打边上色：输入不打断高亮；180ms 防抖后才重算的只是预览与角色跨度，编辑器自身的 token 高亮由增量解析即时完成。
  3. 光标到哪，结构就亮到哪：光标落在某个角色跨度内时，该跨度在源码里显示一条 3px 左侧竖条 + 极淡底色；光标所在行再叠一层更淡的底色。光标落在前言/元数据时不高亮任何结构块，只保留当前行。
  4. 点大纲跳得准：点大纲条目 → 编辑器得到焦点、插入点落到该标题起始偏移、目标标题顶到首行（与今天的行为逐像素一致或更好）。
  5. 滚动同步不失真：编辑器与预览的进度双向同步保持今天的表现；长文档下不再每次测量都重排全文。
  6. 配色集中可调：所有高亮色来自 :root 里的 --syn-* 变量，改一处即全局生效，且不随导入的样式包变化。
  7. 行为零回归：新建/载入示例/打开 .md/另存/重命名、字数统计、会话恢复（文档 + 光标 + 布局）、三种视图模式、两条拖拽分隔条，全部与今天一致。

可读性红线：低对比度的颜色只允许用在结构标记（#、-、>、围栏、分隔线）与元数据上；正文与标题文字必须保持高对比（--ink / --syn-heading）。实现时用一条 e2e 断言把「正文文字颜色 = --ink」钉住，防止以后被配色调整带偏。

7方案与替代

方案对比

方案做法体积工时风险延伸能力与规划一致性
A. CodeMirror 6（推荐） 引入 CM6 作为源码区内核，用 Decoration 承载结构高亮 新增若干依赖，需实测（见 §10 体积基线） 中 中：e2e 与滚动几何要重写 搜索替换、折叠、行号、多光标、快捷键 一致 §15 已选型

C. Monaco VS Code 内核 显著大于 CM6 中 低但重 强，但对 Markdown 场景过剩 偏离 与「体积小」的选型理由冲突

export interface SourceEditorHandle {
  /** 读取当前文档文本。 */
  getValue(): string
  /** 用外部状态覆盖文档（载入示例 / 新建 / 重命名后回写）。 */

  setCursor(offset: number): void
  /** 让某个偏移顶到首行，用于大纲跳转。 */
  revealOffset(offset: number): void
  /** 读取某偏移相对内容顶部的像素位置，用于大纲当前章节判定。 */
  offsetTop(offset: number): number
  /** 当前滚动进度 0–1。 */
  getScrollRatio(): number
  /** 按进度设置滚动位置（预览 → 编辑器）。 */
  setScrollRatio(ratio: number): void
  /** 注册滚动回调，返回解绑函数。 */
  onScroll(listener: (ratio: number) => void): () => void
  focus(): void
}

PR A 只新增这层接口并用现有 textarea 实现它，行为零变化；PR B 换成 CodeMirror 实现，上层 App.tsx 完全不动。这就是把「6 处强耦合」变成「1 个契约」的全部意义。

三条架构约束的核对

约束本方案判定
1. core 不依赖 UI 与宿主CodeMirror 是 DOM 库，只进 apps/demo；core 的 collectRoleSpans 照旧只输出纯数据保持
2. 样式模型只描述数据，不含 CSS 字符串高亮配色放工作台 CSS 变量，不进 theme-schema，schemaVersion 不动保持
3. 预览与导出共用 build() 产出的 HTML只换源码窗格，build()、compileCss、预览注入全部不碰保持

安全边界同样守住：CodeMirror 把文档内容作为文本节点渲染（不写 innerHTML），因此<script> 之类的原文只会被显示，不会被执行；预览侧的转义与 CSP 策略不在本次改动范围内。

12风险与缓解

风险概率影响缓解
滚动几何改动导致大纲高亮 / 双向同步回归（最近三次提交刚做过这块） 高高 P1 先做行为等价重构并保留旧断言；「顶到首行」用既有 e2e 用例逐条对照（滚到顶/滚到底/拖拽宽度后重算）

受控值回环：编辑器 → onChange → state → 编辑器重建，导致光标跳动或输入丢失 中高 受控同步只在「外部值与编辑器当前值不同」时派发最小事务；用 ChangeSet 差量而非整篇替换；IME 组合期间不重建
字体内核差异导致文本排版变化，滚动比例与大纲定位集体漂移 中中 P1 阶段逐项对齐 font-family / size / line-height / padding；用切换前后截图 + 首行/末行位置断言兜住
体积增幅超出预期 中低 先测再评：若 min 增幅明显超出预算，评估按需加载编辑器（动态 import）或缩减语言包（只保留 Markdown）
高亮配色削弱可读性或可访问性 低中 正文不上色（Q4）；结构标记才允许低对比；用断言钉住正文颜色；调色板集中在一处便于评审时整体调整
新依赖引入已知漏洞或不可再分发许可 低中 安装后跑 npm.cmd audit；核对许可证（CM6 与 lezer 均为 MIT）后再提交
