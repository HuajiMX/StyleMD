源码编辑器高亮样式 · 实施规划

2026-10-02 ｜ 仓库：E:\projects\StyleMD ｜ 分支：main（工作区干净）｜ 状态：待评审，未动实现代码

北极星：让工作台左侧的源码区从「一视同仁的灰字」变成「一眼看得出文档结构、也看得见自己正在改哪一段」的编辑器—— Markdown 语法按 StyleMD 自己的调色板上色，光标所在结构在源码里同步高亮；而这次改动不触碰 core、 样式模型、以及预览与导出的共用渲染路径。配色本身要能换——内置几套预设，也允许用户自己在面板里调一套出来。

1范围与边界

本次要做

  • 换掉源码区的编辑内核：把 apps/demo 的受控 <textarea> 换成规划 §15 已选定的 CodeMirror 6。
  • Markdown 语法高亮：前置元数据、标题及其标记、强调/加粗、行内代码、围栏代码块、链接、引用、列表标记、分隔线、表格竖线各有稳定色调。
  • 结构高亮：光标所在「角色块」（复用 collectRoleSpans 的原文偏移）整体淡染 + 左侧竖条，当前行再叠一层更淡的底色。
  • 高亮配色可调：全部颜色收敛为工作台 CSS 变量，一处改、全局生效，为后续深色主题与 M3 代码块主题留接口。
  • 配色可预设、可自定义：内置 5 套配色方案（含一套深色、一套纯灰阶、一套高对比），并提供面板让用户基于任意方案改色、命名保存、随时切回；配色方案与文档样式包彻底分离。
  • 保住既有能力：光标 → 样式卡片定位、编辑器→预览滚动同步、预览→编辑器反向滚动、大纲当前章节高亮、会话光标恢复、字数统计、视图模式与宽度拖拽，逐条回归验证。

本次不做（非目标）

  • 不改 packages/core、packages/theme-schema、packages/presets、packages/renderer-paged：编辑器高亮属于宿主 UI 层，不是渲染内核的职责。
  • 不改 build() 产出的 HTML/CSS，预览与导出路径一行不动（架构约束 3：预览与导出共用同一份 HTML）。
  • 不做渲染输出侧的代码块语法高亮（Shiki），那是规划 §6「代码」行 + M3 的范围；本次只做编辑器里的语法上色，两者共用一份调色板但不共用实现。
  • 不做整体深色工作台主题（功能区、预览外壳仍是浅色）；但允许配色方案把编辑器窗格本身换成深色底，见 §7 的「夜读」预设。
  • 不做搜索替换、多光标批量编辑、代码折叠、行号槽、Vim 键位。
  • 不做 WYSIWYG 或编辑器内嵌预览——本项目定位是「用户继续写 Markdown 源码，只是不用手写 CSS」（规划 §4 假设）。

假设

  • 接受规划 §15 的编辑器选型（CodeMirror 6），本次不重新论证「该不该自己写编辑器」。
  • 允许安装 npm 依赖；允许改 demo 与 e2e 的包内结构。
  • 本机 Chromium 可用，node e2e/smoke.mjs 能跑（沿用既有约定，可用 STYLEMD_CHROME 指定）。
  • 性能目标沿用规划 M2 验收：50 页量级文档，输入延迟 < 50ms、预览刷新 ≤ 300ms。

权限边界

可动：apps/demo/**、e2e/**、apps/demo/package.json 依赖、apps/demo/src/styles.css、本规划文档。
请示后再动：任何 packages/* 的改动、tsconfig.json / vite.config.ts 的别名变更、schemaVersion 与迁移逻辑。
不动：预览 iframe 的沙箱与 CSP 策略（App.tsx 的 PREVIEW_CHROME_CSS / sandbox 注入）。

2待定决策

先看这四条：它们决定工作量和风险面，其余细节都建立在这里的答案之上。决策人：项目所有者。

Q1 · 迁移节奏：分两步还是一次换掉？

一次替换要同时动 App 的 6 处 sourceRef 引用（1 处声明 + 5 个用法）、组件、样式与 17 处 e2e 断言。出问题时很难判断是「抽象没抽对」还是「新编辑器行为不同」。

分两步则是：PR A 只做行为等价的重构（把 HTMLTextAreaElement 换成一层编辑器句柄），PR B 才把实现换成 CodeMirror 6。

建议：分两步。PR A 结束时全部既有测试必须仍然通过，把「重构引入的问题」和「新编辑器引入的问题」隔离在两次提交里；回滚也只需 revert PR B。详见 §10、§15。

相关：§8 方案与替代 · §13 风险

Q2 · 结构高亮要不要和语法高亮同一批交付？

语法高亮解决「读得清」，结构高亮解决「知道自己在改哪个角色」。两者都用 CodeMirror 的 Decoration 机制，共用同一个插件入口；但拆开做要多改一轮 e2e。

建议：同一批交付，但视觉权重分清主次——语法上色用色相区分，结构范围只画到行号槽的竖线上（不在正文里铺底色、不压字），正文只留当前行底色。详见 §6。

相关：§5 目标行为 · §6 交互与视觉

Q3 · 高亮配色归工作台还是归样式包？

样式包（*.stylemd.json）描述的是「文档渲染到纸上的样子」；编辑器是宿主 chrome，用户导入别人的论文样式包，不该顺带改掉自己的工作台配色。

建议：归工作台域，但落点从「一组写死的 CSS 变量」升级为一份可校验、可保存、可切换的配色方案数据（14 个色槽 + 版本号 + 校验），由它注入 CSS 变量。与 M3 的代码块主题预留为同一份调色板源，避免两边漂移。详见 §7、§9。

相关：§7 高亮配色方案 · §9 模型与依赖影响

Q4 · 正文文字要不要也上色？

把整行染成彩色会让长文阅读变累，也让低对比度配色通过不了可读性要求。

建议：正文文字保持 --ink（#17202e）不动，只给结构标记与行内标记上色（#、-、反引号、链接、引用符号）。标题只加粗加深，不改字号，避免行高抖动影响滚动定位。详见 §6。

相关：§6 交互与视觉

Q5 · 配色方案放哪个包？

现有约定是「vitest 只收 packages/*/test/**」，apps/demo 里目前没有任何单元测试位；而配色的校验逻辑（颜色白名单、版本迁移、对比度门槛）恰恰是最该被单测钉住的部分。

建议：新建一个纯数据包 packages/editor-theme（类型 + 5 套预设 + 校验 + 对比度计算 + 版本迁移），与 theme-schema 同构但域不同。代价是加一条 @stylemd/editor-theme 别名（tsconfig.json + apps/demo/vite.config.ts）。若不愿加包，退路是放进 apps/demo/src/lib/editor/ 并接受这部分只有 e2e 覆盖。详见 §8。

相关：§8 方案与替代 · §14 仓库影响清单

Q6 · 自定义方案要不要能带走？

只存在 localStorage 里，换机器或清缓存就没了；但「编辑器配色」又不是文档资产，不该塞进 *.stylemd.json 跟着论文跑。

建议：v1 存 localStorage（方案库用独立键，不随「新建文档」丢失），同时提供单个方案的导出/导入 JSON（*.stylemd-editor.json，2 MB 上限）。不并入样式包——两者语义不同，混在一起会让「导入别人的论文样式」变成一次界面换肤。详见 §7。

相关：§7 高亮配色方案 · §9 模型与依赖影响

Q7 · 用户能改多疯？要不要拦？

开放任意颜色，就一定会有人把正文调成浅灰、把标题调成和底色一样。硬拦会让人烦躁，不拦又违背「可读性红线」。

建议：不阻断，但实时提示：每个色槽旁边显示 WCAG 对比度数值，低于门槛时给黄色警示；提供「恢复到该方案初始值」。内置 5 套预设本身用单测卡住对比度下限，用户自建方案享有自由。详见 §7。

相关：§7 高亮配色方案 · §11 验证矩阵

5目标行为

  1. 打开即上色：文档加载后 1 帧内源码区已按语法着色，无闪烁、无「先黑后彩」的过渡。
  2. 边打边上色：输入不打断高亮；180ms 防抖后才重算的只是预览与角色跨度，编辑器自身的 token 高亮由增量解析即时完成。
  3. 光标到哪，结构就亮到哪：编辑器左侧有行号槽，光标所在角色跨度对应的那些行会在行号右边画出一条 3px 竖线（VS Code 改动条的位置），正文本身不铺底色、不压字；当前行另有一层浅底色。光标落在前言/元数据时不出竖线，只保留当前行底色。
  4. 点大纲跳得准：点大纲条目 → 编辑器得到焦点、插入点落到该标题起始偏移、目标标题顶到首行（与今天的行为逐像素一致或更好）。
  5. 滚动同步不失真：编辑器与预览的进度双向同步保持今天的表现；长文档下不再每次测量都重排全文。
  6. 配色集中可调：所有高亮色来自一组 CSS 自定义属性，由当前生效的配色方案注入；改一处即全局生效，且不随导入的样式包变化。
  7. 行为零回归：新建/载入示例/打开 .md/另存/重命名、字数统计、会话恢复（文档 + 光标 + 布局）、三种视图模式、两条拖拽分隔条，全部与今天一致。
  8. 五套预设随手切：纸感（默认）/ 鲜明 / 黑白 / 夜读 / 高对比，从面板一次点击即全局换色，不需要重建编辑器、不打断光标与撤销栈。
  9. 能改出自己的那套：以任意预设为蓝本新建、逐色槽调色、改名保存、随时切回；每个色槽旁显示 WCAG 对比度，低于门槛只警示不阻断。
  10. 选择记得住：关掉再打开还是上次那套配色；「新建文档」不会把配色方案库清掉；自定义方案可导出成单个 JSON 带走。

7.4 应用机制：改配色不重建编辑器

CodeMirror 的 HighlightStyle 里，每个标签的颜色写成 var(--syn-heading) 这样的变量引用。于是切换方案只需要对工作台根元素重设 CSS 自定义属性：

// apps/demo/src/lib/editor/useEditorScheme.ts（示意）
for (const [name, value] of Object.entries(schemeTokenVars(tokens))) {
  root.style.setProperty(name, value)   // 已验证过的 #rrggbb / #rrggbbaa
}
// 编辑器不重建、文档不重解析、撤销栈不受影响；只是 CSS 变量重算 + 一帧重绘

这条性质直接决定了面板的手感：拖动调色是实时的（无重解析、无重建），也让「改配色」与「改文档」在架构上彻底分开——它进不了文档的撤销栈，也不会把预览拖进重排。

深色方案需要额外一行：night 生效时给编辑器容器加 color-scheme: dark，否则原生滚动条、选区与 IME 候选框仍是浅色皮肤，会露出破绽。

7.6 与样式包、预览、导出的关系（必须说清）

  • 配色方案 ≠ 样式包：样式包决定文档渲染到纸上的样子（预览与 PDF），配色方案只决定你眼前这个编辑器的观感。二者不互相导入、不互相覆盖。
  • 导出与预览完全不受影响：把编辑器调成大紫大红，PDF 里的代码块、标题、表格样式一个像素都不会变。这条要用 export-check 在改配色前后各跑一次来证明。
  • 未来接口留好：M3 引入 Shiki 做渲染侧代码块高亮时，可以让代码块主题提供一个「跟随编辑器配色」的选项，复用同一份 EditorSchemeTokens；但那是样式包域的事，本次不实现。
  • 面板里的措辞很关键：标题下方常驻一句「只影响源码编辑区，不影响预览与导出」，避免用户以为改配色能改论文外观——这类误解比技术缺陷更贵。
