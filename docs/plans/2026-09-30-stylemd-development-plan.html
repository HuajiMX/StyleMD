01范围、非目标与前提

范围内（v1 必须做到）

  • Markdown 源 → 语义角色 → 分页预览 → PDF / PNG / HTML 导出 的完整单机通路。
  • Word 式样式模型：段落样式（结构角色）、字符样式（行内强调/链接/代码）、"基于（继承）"关系、文档默认值。
  • 可视化样式管理器：角色列表 + 实时样式样本 + 分组属性面板；预览中点击元素可直接跳转到该角色的样式。
  • 文档级页面设置与页眉页脚：纸张、方向、页边距、分栏、页码域（含总页数）、封面独立页眉页脚。
  • 样式包（*.stylemd.json）的导入 / 导出 / 内置预设 / 版本迁移。
  • 桌面端应用（Windows 优先），核心库保持宿主无关，可被 Web / CLI 复用。

非目标（明确不做，避免范围蔓延）

  • 协同编辑、账号体系、云同步、团队权限。
  • Word 那样的"直接编辑排版结果"的富文本编辑：v1 仍是 Markdown 源码编辑 + 只读交互式预览。
  • 与 Microsoft Word 100% 排版兼容；.docx 不作为一等格式（列为 M5 试探项）。
  • 第三方插件运行时与主题市场；v1 只提供样式包（数据，不是代码）。
  • 参考文献管理（Zotero / BibTeX 抓取）与公式可视化编辑；仅提供既有 LaTeX 语法的渲染与样式化。
  • 移动端、纯在线版正式发布。

前提假设

  • 目标用户愿意继续写 Markdown 源码，只是不想手写 CSS；"可视化配置样式"是核心价值，编辑器本身不需要颠覆。
  • 排版精度要求到 pt/mm 级别：中文行距、首行缩进 2 字符、三线表、图题居中、页码位置等都需要精确可控。
  • 单文档常见 5–50 页，上限按 300 页设计；纯本地运行、可离线导出。
  • 本机环境实测：Windows + Node v24.11.1；PowerShell 已禁用 npm.ps1（脚本必须用 npm.cmd）；无 Rust / Cargo；pandoc 可用（来自 Anaconda）。

02待决问题与建议默认值

这些问题在写代码前值得花 10 分钟确认。每条都给了推荐默认值——若不回复，后续按"推荐"推进。

Q1 · 宿主（壳）选型：Electron、Tauri、Qt，还是不要壳？

部分已决

已决（2026-09-30）：渲染引擎采用 Chromium（Paged.js 分页 + Chromium 打印管线）。待决：承载它的壳。关键判断是——体积差异不来自"用不用 Electron"，而来自"要不要自带 Chromium"：自带 Chromium 的 Electron 与 Qt WebEngine 在同一量级（官方分发包分别实测 150.7 MB 与 160.4 MB），借系统 WebView 的 Tauri 只有 ~5–10 MB，但只有 Windows 借到的是 Chromium（macOS/Linux 是 WebKit）。

建议：不要把宿主选择和 M0/M1 绑在一起。M0 用浏览器原型 + 命令行导出验证分页，M1 只写宿主无关的核心库；把定案推迟到 M2 开工前。届时默认选 Electron（全平台同一个 Chromium、printToPDF 一等公民、纯 TS 开发成本最低）；若体积是硬指标且愿意放弃 macOS/Linux，再考虑 Tauri + WebView2。详见 §5 D1b。

影响：架构分层、打包分发、自动更新策略。详见 §5、§5 D1b、§7、§13。决策人：项目所有者（建议在 M2 前定）。

Q2 · 首要场景：通用技术文档，还是学位论文 / 公文？

影响默认模板

建议：v1 内置两套预设——「通用技术文档」（Markdown 原生语义即可覆盖）与「中文学位论文」（需要扩展语法）。若只能选一个，选技术文档：它的结构完全落在 Markdown 原生语法上，能最快跑通全链路；论文场景需要"摘要/关键词/图题/表题/参考文献"等语义扩展，投入更大但差异化最强（现有编辑器几乎都不支持"给图题单独配样式"）。

影响：语义层设计（§8）、内置样式包、验收用例（§11）。决策人：项目所有者。

Q3 · 是否把 DOCX 作为输出目标？

成本项

建议：v1 不做。先用 M0 验证"样式模型 → PDF"闭环；DOCX 作为 M5 的试探性后端（样式模型 → Word styles.xml，尽力映射，声明不保证逐像素一致）。理由：Word 的样式/编号模型与 CSS 不完全同构（编号是独立于样式的实体），要真正做好是另一个大工程，会拖慢核心价值交付。

影响：M5 范围与工作量（§10）。决策人：项目所有者。

Q4 · 分页内核：引入 Paged.js，还是直接用浏览器原生分页？

M0 验证

建议：默认走 Paged.js（在 Chromium 内实现 CSS Paged Media：页边距盒、页码域、target-counter 目录页号、脚注、跨页控制），代价是长文档分页性能需要专门治理。M0 必须双轨验证：同一份文档分别用 Paged.js 与"原生 @page + Chromium 页眉页脚模板"出 PDF，比较页码/页眉/目录页号的可实现性与 300 页耗时，用数据定案。

影响：预览架构、导出实现、性能预算（§7、§12）。决策人：实施方出结论，项目所有者确认。

Q5 · 是否需要无界面的批量导出（CLI）？

建议纳入

建议：要。核心库无 UI 依赖的前提下，CLI 只是薄壳（读取 Markdown + 样式包 → 输出 PDF），能顺带覆盖 CI 出报告、批量转档、服务端渲染等用法，且成本很低。

影响：核心库 API 边界与打包方式（§7）。决策人：项目所有者。

Q6 · 开源协议与字体策略？

合规

建议：代码 MIT；内置字体只打包可再分发的开源字体（思源宋体/黑体、Noto 系列），并提供"使用本机已安装字体"的选项，不打包任何商业字体。安装包里的每个字体都要有来源与许可记录。

影响：分发合规、安装包体积、字体回退策略（§12、§5 D1b）。决策人：项目所有者。

Q7 · 扩展机制做到什么程度？

可延后

建议：v1 只做"数据级扩展"（样式包 JSON + 自定义 CSS 注入作为逃生舱），不做代码插件运行时。等样式模型稳定并出现真实需求后，再考虑插件 API。

影响：安全面（注入执行）、API 稳定性承诺（§12）。决策人：项目所有者。

05推荐方案与备选（关键决策）

D1 · 渲染管线（已确认：Chromium 打印管线）

已确认（2026-09-30）：渲染引擎采用 Chromium——分页预览与 PDF 导出共用同一条 Chromium 渲染/打印管线。下表的备选对比保留下来，作为"为什么不是别的方案"的决策记录。

候选预览一致性富样式表达力页级特性分发体积结论
A. HTML/CSS + Paged.js + Chromium 打印 极好（预览与导出同一引擎） 极好（CSS 天生覆盖边框/底纹/缩进） 中（Paged.js 补齐页码域/目录/脚注） 自带 Chromium：官方分发包 150.7 MB 推荐主干
B. Typst 后端 差（必须另写预览器，双引擎易不一致） 好（模板函数需自行映射） 好（原生页眉页脚/目录/脚注） 小（单二进制） 列为 M5 可选后端
C. LaTeX（Pandoc） 差 中（富文本样式映射痛苦，需 tcolorbox 等） 极好 极大（TeX 发行版 GB 级） 不采用
D. Prince XML 好 极好 极好（最完整的 CSS Paged Media） 小，但商业授权昂贵 保留为"高保真商业版"可选授权路径
E. 纯 JS PDF 库（react-pdf / pdfmake） 极好（同引擎） 中（一切排版需自研：断行、分页、孤行） 需全部自研 小 备选：若 Paged.js 性能不可接受再评估

决定性理由：本产品的核心承诺是「所见即所得的分页预览」。只有当预览与导出共用同一个排版引擎时，这个承诺才不需要靠无穷无尽的补偿技巧来维持。方案 A 让 CSS 成为样式模型的编译目标，而 CSS 恰好是"边框、底纹、缩进、行距、分栏、页边距"表达力最强的声明式语言。

D1b · 宿主（壳）选型：Chromium 是硬约束，壳是可替换的

渲染引擎已确定为 Chromium，于是宿主选型的问题被简化成一句话：要不要自带 Chromium。自带 Chromium 的方案（Electron、Qt WebEngine）体积落在同一量级；借系统 WebView 的方案（Tauri）体积小一个数量级，但只有在 Windows 上借到的才是 Chromium。以下数据均为 2026-09-30 定向核验的官方来源（见 §15）。

宿主渲染引擎实测 / 官方体积一键导出 PDF开发成本结论
Electron 自带 Chromium，全平台同一版本 官方分发包 electron-v44.5.1-win32-x64.zip = 150.7 MB（darwin-arm64 124.2 MB、darwin-x64 128.0 MB、linux-x64 117.2 MB）；NSIS 安装包经压缩后通常更小 webContents.printToPDF(options)，支持 pageSize / margins / printBackground / displayHeaderFooter 低（纯 TS / 前端栈） 推荐默认
Tauri（Windows 限定） WebView2 = Chromium ✔
官方原文：Tauri uses WebView2 which is based on Microsoft Edge and therefore Chromium		 ~5–10 MB 量级（不含运行时；Windows 11 已预装 WebView2） 需自建：Rust 侧 with_webview 拿到 WebView2 接口 → ICoreWebView2_7::PrintToPdfAsync；Tauri 自身只暴露 print（打印对话框） 中（需要 Rust 工具链，本机未安装） 体积硬约束下的候选
Tauri（跨平台） macOS = WKWebView、Linux = webkit2gtk（WebKit，非 Chromium） ~5–10 MB 量级 各平台各自实现，分页结果不一致 中高 与 Chromium 渲染承诺冲突
Qt 6 + WebEngine 自带 Chromium（Qt WebEngine 基于 Chromium） 无体积优势：含 WebEngine 的 pyside6_addons-6.11.2-win_amd64.whl = 160.4 MB，与 Electron 同量级甚至更大 QWebEnginePage::printToPdf() 一等公民 高（C++/QML 或 PySide 栈 + Qt 部署 + LGPL/GPL 合规） 不推荐
浏览器版（无壳） 用户自己的 Edge / Chrome（Chromium） 0 MB 浏览器打印对话框「另存为 PDF」；页码与页眉页脚由 Paged.js 画进页面，可在对话框里关掉浏览器自带的页眉页脚 最低 M0 原型首选

结论：Qt 在体积上没有任何优势（同样自带 Chromium，还要额外承担 UI 栈、Qt 部署与许可合规），排除；Tauri 只有在"只做 Windows"或"接受跨平台分页不一致"时才成立；Electron 是唯一同时满足"全平台 Chromium + 一键导出 + 低开发成本"的选项。

但不必现在定壳。§7 已约定核心库与宿主无关，因此宿主选型是可逆决策，建议把决策点推迟到 M2 开工前：M0 用浏览器原型 + 命令行导出验证分页，M1 只写纯 TS 核心库，两者都不依赖宿主。届时按实测体积与目标平台再定，切换成本几乎为零——这正是"核心与宿主解耦"这条约束换来的自由度。

若最终选 Electron，体积优化清单（M2 执行）

  • electronLanguages（electron-builder 配置）：只保留 zh-CN / en-US，其余 locales/*.pak 会被删除（源码已确认该行为，并有"全删光时跳过清理"的自我保护）。预计节省 10–25 MB，以实测为准。
  • NSIS 目标 + 最大压缩；用 asar 打包，避免把源码树原样塞进安装包。
  • 不要在同一个项目里引入第二份 Chromium（例如为了 CLI 导出再打包 Puppeteer / Playwright）：CLI 导出复用同一个 Electron 二进制，或直接用系统浏览器。
  • 保留 LICENSES.chromium.html，不要为了省十几 MB 去掉许可文件。

要诚实面对的事：只要承诺"全平台 Chromium 渲染"，安装包就在 100 MB 量级——这个代价无法靠换壳绕开（Typora、Obsidian、VS Code 都在这条线上）。如果体积是硬指标，真正该改的是发布形态而不是壳：浏览器版 0 MB，Tauri + Windows-only 约 10 MB。

D2 · 样式模型与渲染后端解耦（本规划最重要的一条架构约束）

样式模型是产品的核心资产，必须是纯粹的数据：描述"角色 → 属性"的树，不含任何 CSS 字符串、DOM 或引擎概念。后端只负责"把模型翻译成目标格式"：

后端输入输出阶段
CSS 后端（默认）样式模型 + 语义 HTML分页预览 + PDFM1–M4
DOCX 后端样式模型styles.xml + 文档M5（可选）
Typst 后端样式模型.typ 模板 + PDFM5（可选）
HTML 后端样式模型带内联样式的自包含 HTMLM4（低成本附赠）

这条约束的价值：日后用户抱怨"PDF 里的表格跨页不好看"时，可以只换后端，而不动界面和样式模型。反过来说，如果样式面板的每个控件都直接写死成一段 CSS，产品就永久锁死在 Chromium 上了。

D3 · 参考实现：Word 的样式语义

Word 概念StyleMD 对应原因
段落样式（标题 1 / 正文 / 题注）结构角色样式（role: heading.1 / paragraph / figure.caption）与 Markdown AST 节点一一对应
字符样式（强调 / 超链接）行内样式（inline.strong / inline.link / inline.code）行内语义在 Markdown 里是独立标记
样式基于（based on）basedOn 继承链，最多 4 层，禁止环改"正文"能带动所有衍生样式
文档默认值document.defaults（字体、字号、行距、文字色）所有样式的最终兜底

明确的差异：Word 把"编号（编号格式、多级列表）"作为独立于段落样式的实体，StyleMD v1 简化为"样式内联编号定义 + 文档级编号表"，并在文档中说明这一简化，避免用户误以为与 Word 完全同构。

分层原则（三条硬约束）

  1. 核心库不依赖 UI 与宿主：packages/core 只做纯函数式的"输入 → 输出"，不 import React、不依赖 Electron API。这样才能被 CLI、Web、CI 复用，也才能被单元测试完整覆盖。
  2. 样式模型不含 CSS 字符串：所有属性用结构化字段表达（见 §8），CSS 只是编译产物。禁止在样式模型里出现 "border-bottom: 1px solid #888" 这样的字符串。
  3. 预览与导出走同一个渲染函数：导出的 HTML 由预览所用的同一段代码生成，避免"两套模板慢慢漂移"这一经典失效模式。

语义层：Markdown 表达不了的语义怎么办

Markdown 原生只有标题/段落/列表/引用/代码/表格/图片。论文与公文场景还需要"摘要、关键词、图题、表题、参考文献条目、致谢"等可被单独配置样式的结构。方案：

  1. 容器指令（remark-directive）：::: abstract … :::、::: keywords，渲染为 section[data-role="abstract"]。
  2. YAML frontmatter：title / author / affiliation / date / toc: true，映射到封面与页眉页脚的文档元数据。
  3. 自动角色识别（启发式，可在 UI 里关闭）：紧邻图片的斜体段落 → 图题；以「表 x-x」开头的段落 → 表题；位于「参考文献/References」标题之后的编号段落 → 参考文献条目。
  4. 优雅降级：所有扩展语法在普通 Markdown 阅读器里仍应呈现出可读结果（例如 ::: abstract 降级为普通段落/引用），保证文档不被工具锁死。

注意：自动识别必须有"这条段落被识别成了什么角色"的可视反馈，并且用户能一键改判。否则用户会陷入"样式改了却看不到效果，因为那段其实被判成别的角色"的困惑——这是这类工具最常见的使用挫折。

验证清单（每条都要有可复现的 demo 与结论文档）

  3. 目录页号：target-counter(attr(href), page) 是否可用、刷新后是否准确。

  6. 性能基准：1 / 20 / 100 / 300 页文档，分页耗时与内存曲线；确定"分块分页 + 虚拟化"是否必需。

  • packages/theme-schema：样式模型类型、JSON Schema、校验（含 basedOn 环检测与跨类继承拒绝）、版本迁移骨架。
  • packages/core：解析 → 角色化 → 样式解析（继承 + 覆盖 + 默认）→ HTML 渲染 → CSS 编译。锁定 §7 的对外契约。
  • 语义层 v1：frontmatter、容器指令、图题/表题/参考文献的启发式识别 + 角色回退。
  • 确定性与安全：同一输入必得同一输出（可快照）；原始 HTML 走消毒白名单。

验收：DoD #1 通过（全程不写 CSS 完成一级标题的六项调整）；样式包往返测试无损；导入非法 JSON 给出可读报错而非崩溃。

12风险与对策

风险概率影响缓解措施兜底方案
Paged.js 长文档性能不可接受（300 页卡顿）中高 M0 先测；分块分页 + 虚拟化预览；编辑时只重排当前页附近 回退原生浏览器分页 + 页眉页脚模板；或评估自研分页
分页特性覆盖不足（表格跨页表头、脚注、图文环绕）高中 UI 对 ⚠ 项显式标注"尽力而为"；建立分页边界用例集持续跟踪 把该能力降级为 M5，或以"导出后手动微调"说明替代
中文字体：字重缺失、合成粗体、标点避头尾不符预期高中 内置开源中文字体（思源系）；字体可用性检测与缺失告警；提供字重回退策略 允许绑定本机字体；导出前预检并提示替换
预览与导出逐渐漂移（两条渲染路径）中高 硬约束：共用 renderHtml；视觉回归纳入 CI 必过项 若漂移发生，以 PDF 为准并暂停发版直到回归恢复
样式模型设计不当，后续无法扩展（最大长期风险）中高 M1 阶段先把"Word 概念 → 模型"映射表定稿并写进文档；模型里禁止出现 CSS 字符串；schemaVersion 与迁移机制从第一天就在 模型小幅演进用迁移脚本；大改则并行引入 v2 并双读一段时间
与 Word 心理预期不一致（用户以为行为应该一样）中中 文档明确差异清单（编号模型、图文环绕、样式覆盖范围）；界面用语与 Word 保持一致以降低学习成本 DOCX 导出作为"要 Word 就去 Word"的出口
Electron 安装包体积与启动速度被用户抱怨中低 对比 Typora/Obsidian 的既有接受度；按需加载预览模块 提供"轻量 CLI + 浏览器版预览"的替代路径
Markdown 原始 HTML 带来的安全面（本地文件读取、注入）低高 渲染期消毒白名单；预览用 sandbox 化 WebView，禁用 Node 集成；导出进程无网络 默认禁用原始 HTML，需在设置中显式开启
字体与依赖许可问题影响分发低中 只打包可再分发字体；集中维护第三方许可清单 改为"引导用户安装字体"而不随包分发
范围蔓延（一路做到 DOCX/插件/云同步）高高 以 DoD 十项为唯一交付口径；M5 明确标为可切 每季度重排一次优先级，未进 DoD 的需求默认进 backlog

术语表

术语含义
角色（role）文档结构的语义标识，如 heading.1、body.text、figure.caption。样式挂在角色上。
样式模型描述"角色 → 属性"的纯数据（JSON），不含任何 CSS 字符串，可迁移到不同渲染后端。
样式包（theme）一次可分发的样式模型实例，文件后缀 *.stylemd.json。
基于（basedOn）样式之间的继承关系，类似 Word 的"样式基于"。
分页预览把 HTML 切成真实纸页尺寸的预览，与导出的 PDF 对应页一致。
域（field）页眉页脚中会自动求值的占位内容，如页码、总页数、文档标题、日期。
